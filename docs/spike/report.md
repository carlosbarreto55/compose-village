## Out-of-process comparison

The same workload runs in this JVM (*in-process*, the game's own JVM) and in a helper JVM started from the
game's classpath (`CompileServer`, out-of-process). The helper runs the identical `PlayerPipeline` + `PreviewEngine`
and returns diagnostics and a PNG frame over a length-prefixed stdin/stdout protocol. Times are measured on the
host until the frame can be shown, so the helper's numbers include the round trip and decoding the PNG into an
`ImageBitmap`. Workload: the ~30-line counter app; 30 warm compiles, then 30 synthetic clicks.
In-process ran first, when this JVM had not compiled or rendered anything yet. Raw samples: `outofprocess.csv`.

Helper faults are simulated with spike-only requests, because the sandbox and the guard block their real causes:
`exit` calls `System.exit(0)` (a sandbox escape), `oom` allocates until the heap is exhausted (the helper runs with
`-XX:+ExitOnOutOfMemoryError`), `wedge` spins forever on the helper's request thread (a hung compile or render),
which the game detects with a 3 s request timeout and then kills the helper. *Recovered* is the time to spawn a
new helper and get the next attempt's first frame, which is a cold compile again.

## Memory over 150 reloads

Each cycle compiles the ~30-line counter app (a different literal per cycle, so every attempt has its own
classes), verifies and loads it, renders it and clicks it twice, then closes the scene. Samples are taken after
`System.gc()` at the end of each cycle. Limits are what leaking 10 % of the attempts after cycle 20 would
add (per attempt: ~10 classes, ~100 KB Metaspace, a ~0.9 MB frame).

Metaspace is judged in a C1-only control run: with the default tiered JIT it keeps growing slowly (decelerating)
because the host's own hot code accumulates profiling metadata in the app class loader's non-class Metaspace,
while class space and the class count stay flat. A leaked attempt would add classes and class space instead.
RSS is recorded only: it is noisy (heap the JVM does not return to the OS, JIT code cache), and in the control
run, which renders the same scenes, it stays flat, so frames are not leaking native memory.
Per-cycle series: `memory.csv` (default JIT) and `memory-c1.csv` (control).
