## Context

`add-level-domain` (archived 2026-10-12) gave us:
- level data: `levels/` resources, an index, `level.json` with criteria, and `Starter.kt`;
- test-only `Solution.kt` files, checked by `LevelsTest`;
- a pure `Evaluator` over a `SemanticsSnapshot`;
- a throwaway level mode in the spike window: Sandbox/level chips, a request card, and a verdict panel showing ✓ id / ✗ message.

The Console and Recompositions panels are always visible.

The explore session settled these decisions:
- the target is pre-rendered at build time, so solutions stay out of the game;
- failure details are generated by the evaluator;
- panel unlocks are derived from level order, with no saved state;
- Continue opens the next indexed level, and the last level says more are coming.

This design explains how to build them.

## Goals / Non-Goals

**Goals:**
- The player always sees the goal: a ghost before the first Run, and a "Your screen | Target" switch to look at it full size.
- Checklist lines written by authors (`description`), with failure explanations generated generically, so new levels never need new code.
- A clear "Level complete" state, and a Continue button through the indexed levels.
- Panels appear only when a level needs them, with a small unlock moment.
- Two levels, to prove that a level with different requirements needs only data.

**Non-Goals:**
- Saved progress, a level-select screen, and persistent "seen" state. These are for a later change.
- Comparing pixels against the target for any purpose.
- Replacing the spike window with final game UI or art.
- Interaction criteria (click, then check) and console-output criteria.

## Decisions

### D1. Targets are rendered by a build step, not in the game
```
levels/src/targets/kotlin/RenderTargets.kt  (own source set: main classes + compiler + preview)
   reads  src/main/resources/levels/**  +  src/test/resources/levels/<id>/Solution.kt
   writes build/generated/level-targets/levels/<id>/target.png     (2× density, level viewport)
                │
   processResources.from(renderTargets)  ──▶ levels.jar: levels/<id>/target.png
```
- **A separate `targets` source set**, run by a `JavaExec` task named `renderTargets`. It can't use the test source set: test compilation depends on main's processed resources, and those would depend on the render task, which would create a cycle. The `targets` source set depends on main's *classes* only, plus `:compiler`. It reads level data straight from the source directories through `LevelFiles.directory`.
- The task's inputs are the level resources, the solutions and the runtime classpath. Its output is the generated directory, so Gradle skips it when nothing changed. It fails if a solution doesn't compile or render.
- **Density 2×** stays sharp on Retina displays. The game draws the image at the viewport's dp size.
- `LevelFiles` gains `readBytes`, and `Level` gains `targetPng: ByteArray?`. It is null for fixture levels in unit tests. `LevelsTest` asserts that every bundled level has one.
- The app decodes the PNG into an `ImageBitmap` once, when the level opens, and keeps it in the controller. This is the whole of "render once and cache".

*Alternatives:*
- Ship `Solution.kt` and compile it when a level loads. Rejected: the solution would be readable from the jar, a cold compile could take about 2 s, and it would contradict the spec.
- Commit the PNGs. Rejected: they could drift from the solutions.
- Ship a target snapshot and draw boxes from it. Rejected: it doesn't look like the goal.

### D2. Description is authored; the failure detail is generated
`Criterion` gets `description: String` (required) and `message: String?` (optional, the villager's line). `CriterionResult` becomes `(id, description, passed, detail: String?, message: String?)`. The evaluator computes a `Failure` reason while it checks each criterion, then phrases it:

```
check(c) ──▶ Pass | Missing(sel) | Hidden(sel) | Count(sel, n, m) | Present(sel)
                  | Reversed(a, b) | NotInLine(a, b)         ──▶ phrase(reason) ──▶ detail
```

- **Hidden versus Missing**: a selector matches a node in the snapshot, but no *visible* node.
- **Reversed**: some pair satisfies the opposite order.
- **NotInLine**: both sides are visible, but neither order holds.
- **Noun phrases** come from the selector:
  - text → `"Rosa's Bakery"`;
  - role + text → `a button "Order"`;
  - role only → `a button`;
  - content description → `an image described as "logo"`.

  The role words come from a small table, one entry for each of the 9 role names. With `contains`, the phrase is `a text containing "…"`.
- Details are written in the game's voice, in English, and stay generic. `message` lets authors add flavor without the evaluator needing per-level code.

### D3. `below` and `rightOf` are decoded as their own types and evaluated by swapping
These are four serializable classes. `Below(a, b)` is evaluated as `Above(b, a)`, but phrased with the author's `a` and `b`, so the details read like the description ("X is above Y" for a reversed `below`).

### D4. Panels: the level lists only the extras
`panels: List<Panel>` with `enum Panel { CONSOLE, RECOMPOSITIONS }`, serialized in lowercase. The loader rejects unknown or repeated names, listing the valid ones. The preview, target, checklist and problems list are always present for levels. The sandbox shows all panels and never highlights.

**Unlocks are derived**: `LevelRepository` computes `unlocks: Map<Panel, String>`, mapping each panel to the first level id in index order that lists it. When a level opens, the screen highlights each panel whose unlocking level is this one. The highlight is a pulsing primary-color border plus a callout with the panel's explanation and a "Got it" button, and it auto-dismisses after about 8 s. The explanation texts live in the app:
- Console: "The Console shows what your code prints with `println`. Use it to see what your code is doing."
- Recompositions: "This panel counts how often each of your composables runs. Fewer runs means a snappier screen."

*Alternative:* persist the panels the player has seen. Deferred: that is the first piece of saved player state, and it belongs with progress saving.

### D5. Level screen layout and states
```
┌ toolbar: [Sandbox] [Hello Main Street] [Open Sign]   Run ⌘↩   timings ┐
├ request card (resident, request)          │ [ Your screen | Target ]          │
│                                           │ ┌ preview (viewport) ─────────────┐│
│ editor                                    │ │ ghost / frame / target          ││
│                                           │ └─────────────────────────────────┘│
│                                           │ ┌ checklist / Level complete ─────┐│
│ problems list                             │ │ ○/✓/✗ description · detail       ││
│                                           │ └──────────────────────────────────┘│
│                                           │ [Console]  [Recompositions]  (if listed)│
```
- **Ghost**: before the first frame of this level (state `frame == null && error == null`), the preview draws the target at an alpha of 0.25, with the caption "Rosa's sketch: press Run to build it". The name comes from `resident`.
- **View switch**: a Material3 segmented button above the preview, "Your screen" or "Target". "Target" draws the target at full opacity instead of the frame, and the pane's `pointerInput` stops forwarding events to the scene. Opening a level and starting a Run switch back to "Your screen". A thumbnail next to the preview and a 50% overlay were tried first; the thumbnail was too small to read and took width from the editor, so the switch replaced both.
- **Checklist**:
  - Before the first Run, each line shows ○ and its description.
  - After a Run, each line shows ✓ or ✗ and its description. A ✗ line also shows the detail, then the message in italics.
  - `NotRun` shows a single line: "didn't compile" or "crashed".
- **Level complete**: the card switches to the primary container color and shows "Level complete!", a short line ("Rosa loves her new sign"), the ✓ list and a Continue button. On the last level, it shows "More of Main Street is coming soon" instead of Continue.
- **Continue** calls `controller.open(next)`, which replaces the editor with the next level's starter code and resets the verdict, ghost and highlights.
- The preview column is as wide as the level's viewport (at least the sandbox's 360 dp).

### D6. Content
- **Level 000** becomes two criteria: `exists title` ("The text \"Rosa's Bakery\" is on screen") and `below order` (a = "Fresh bread daily", b = "Rosa's Bakery", "\"Fresh bread daily\" appears below \"Rosa's Bakery\""). The redundant `subtitle` check goes away. Its solution becomes plain `Text`s, so the target matches what is checked.
- **Level 001 `001-open-sign`**:
  - Tom the florist: "Put \"Tom's Flowers\" on my sign with an \"Order\" button to the right of it. When someone presses Order, print \"New order!\" so I hear the bell."
  - Criteria: `exists` text, `exists` button with role + text, and `rightOf` button/text.
  - Panels: `["console"]`.
  - The `println` part is flavor for the unlocked Console. No criterion checks console output (non-goal).

### D7. Tests and checks
- **Evaluator unit tests**: one per failure reason and phrase, the `below`/`rightOf` aliases, and descriptions and messages in results.
- **Loader tests**: a missing `description`, a blank `message`, unknown and repeated panels, defaults.
- **`LevelsTest`**: every level has a target of `viewport × 2` pixels, and the index has the two levels in order.
- **Unlock derivation**: tested with fixture indexes.
- **Harness window section**, through the real window:
  - opening level 000 shows the target and ghost before Run, with no Console or Recompositions;
  - the starter gives two ✗ with "can't find" details;
  - the wrong order gives a "reversed" detail;
  - the solution shows Level complete;
  - Continue opens 001, with the Console visible and highlighted;
  - screenshots of each state.

## Risks / Trade-offs

- **Targets render with the build machine's fonts.** A build on Linux would ship a slightly different-looking target. → Release builds are macOS-only today, and the target is for display only, never compared.
- **Builds get slower when level data changes**, because the render step compiles every solution (a few seconds). → The step is up-to-date-checked, and it reuses one pipeline and one engine for all levels.
- **Generated English details limit localization.** → Phrases live in a single file and can be swapped out later.
- **A full-size target invites pixel-perfect matching.** → Solutions show only what is checked (an authoring rule in the spec), and a passing attempt is "Level complete" whatever its styling.
- **Derived unlocks re-trigger on replay.** For example, opening 001 again highlights the Console again. → This is accepted until saved progress exists.
- **Level 001's `println` request isn't checked.** → This is stated in the design. Console criteria can come with interaction criteria.

## Migration Plan

The level format changes in place. `message` becomes optional and `description` is required. Both bundled levels are updated in the same change, and there are no released levels or saved data. To roll back, revert the change.
